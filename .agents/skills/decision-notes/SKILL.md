# Decision Notes

决策笔记保存**代码和测试无法可靠推导出的「为什么」**:设计意图、不能破坏的边界、被否决的方案。

存在的理由:每个新会话都没有历史记忆,只能看到眼前的代码。一段写得别扭的代码,往往是为了避免死锁或兼容某个约束而故意为之,不知情的 Agent 会把它「优化」掉;三个月前被否决的方案,也会被一次次重新提出。笔记就是留给下一个会话的护栏。

它不是工作日志。不记录今天做了什么、改了哪些文件、思考过程、TODO 或进度,这些属于 PR 描述。

笔记放在扁平目录 `.agents/decisions/`。目录不存在表示项目还没有决策笔记;首次需要记录时创建它。自动校验是可选的项目工具,不要求特定语言或包管理器;何时调用及未接入时的处理见第 7 节。校验只管结构与引用,内容好不好由你自己负责。

## 1. 改已有代码之前:先查一次

无论任务大小都做,因为最容易误改的恰恰是「看起来只是小重构」的任务。

如果 `.agents/decisions/` 不存在,表示暂无笔记,可以结束检索;首次需要记录时再创建目录。否则:

1. 先找 `Applies-To: project-wide` 的笔记。
2. 检查各笔记的 `Applies-To`,把其中的仓库相对路径或 glob 与这次要改的文件逐一匹配。`rg` 可以帮助找出字段和字面路径,但不会替你解释 `Applies-To` 中的 glob,不要把一次文本搜索宣称为完成了 glob 匹配。
3. 要改的文件里如果有 `Decision: <文件名>.md` 注释,读它指向的笔记。
4. 再按路径片段和领域关键词补充搜索(没有 `rg` 就用 `grep -ril`):

```bash
rg -il --hidden --no-ignore -e "src/worker" -e "worker" -e "ipc" .agents/decisions
```

5. 命中后只需先读 `Status`、`Applies-To` 和 `Decision` 三处,确认相关再读全文。

查到之后怎么处理:

- **accepted**:当作当前约束遵守。如果这次改动会违反它,先判断用户是否已授权这项技术选择、迁移或委托你选型;已授权就继续实施并新建笔记取代它。只有冲突超出授权范围,或仍有未解决的需求分歧、必须由用户决定取舍时,才停下来说明冲突并询问。不要悄悄绕过或改掉原结论。
- **rejected**:不要重新提出。只有前提确实变了才可以重提,并在新笔记里写明哪些前提变了。
- **superseded**:只当历史看,顺着 `Superseded-By` 找到现行的那篇。
- **proposed**:还没定案,不要当作既定约束。

## 2. 什么时候需要写笔记

判断标准:

> 未来的 Agent 看到这段代码或这个契约,会不会想去简化它、绕开它,或者重新提出一个已经否决过的方案?会,就写;只看代码和测试就能理解原因,就不写。

通常需要写的改动:

- **架构边界**:模块如何依赖、进程如何通信、层与层的边界。
- **跨模块契约**:API、事件、协议、接口、schema。
- **持久化契约**:数据库 schema、配置文件格式、文件格式、wire protocol。
- **重要技术选型**:SQLite 还是 JSON、IPC 还是 HTTP、用哪个 Runtime。
- **非显然约束**:为什么这里不能并发、为什么故意不用缓存、为什么必须走某层抽象。

通常直接改代码,不新建笔记:格式化、样式、拼写、简单重命名、普通 CRUD、局部 bugfix、简单类型修复、补测试、依赖 patch 升级、文案、纯机械重构。若这些改动改变了已有笔记中的名称、路径或行为事实,仍需按第 3 节判断是更新原笔记,还是新建并取代。

拿不准时倾向不写。笔记太多没人读,比少写一篇代价更大。

## 3. 更新还是新建

先看第 1 步查到的结果,只有三种情况:

- **已有笔记描述的就是这个决策**:就地更新,不要新建。只是非核心的命名、路径或实现细节变了,直接改原笔记里的事实。
- **已有笔记相关,但这是一个新的独立决策**:新建,并在正文里用相对链接引用旧笔记。
- **没有相关笔记**:新建。

判断「是同一个决策还是新决策」的依据:`Decision` 一节里的**核心结论**变了没有。结论变了(比如 IPC 换成 Message Bus),就新建一篇并取代旧的;结论没变只是细节变了,就原地更新。

取代旧决策时,旧笔记保留原文不删,只做两处修改:`Status: superseded`,并加一行 `Superseded-By: ./新文件名.md`。旧笔记里「曾经为什么那样设计」仍然有价值。只是部分取代时,不要标 superseded;在适用范围确实变化时改窄旧笔记的 `Applies-To` 和 `Decision` 范围,并让新旧笔记相互链接。保留旧笔记对历史选择的解释。

`rejected` 和 `superseded` 是两条不同的轨道。`superseded` 表示方案**曾经生效**、现已被新决策取代,取代链的终点必须落在 accepted 笔记上(校验器 D103 强制)。`rejected` 表示方案讨论过但**从未生效**,因此它不能出现在取代链里:候选方案被否决时,旧笔记保持 `accepted` 不动,把被否决的那篇写成 `rejected` 即可。若一个已经落地生效的方案后来被回退,它的状态是 `superseded` 而不是 `rejected`——新建一篇 accepted 笔记说明回退后的现行方案,再把它设为被回退那篇的 `Superseded-By`。

笔记原则上不删除。决策失效通常用取代或改窄 `Applies-To` 表达,而不是抹掉原文。只有当决策对象整体消失(功能下线、模块删除)且保留它只会误导检索时才删除;删除前确认没有代码里的 `Decision:` 指针指向它,并改掉指向它的 `Superseded-By`,否则校验器会报 D110 / D101。原文仍留在 git 历史里,需要时还能查回。

## 4. 笔记格式

文件名 `YYYY-MM-DD-short-topic.md`,日期是首次创建日(在 bash 用 `date +%F`,在 PowerShell 用 `Get-Date -Format yyyy-MM-dd`,不要凭印象),主题用小写英文 kebab-case,描述决策主题而不是任务本身。

```markdown
# Decision: <标题>

Status: accepted
Applies-To: src/worker/**, src/ipc/protocol.ts

## Context

为什么需要做这个决定:问题、约束、触发条件。

## Decision

现行方案是什么,边界在哪。

## Alternatives

- **方案 A** — 为什么看起来合理(对手最强的论据);为什么最终没有采用。
- **不做 / 复用现有方案** — 为什么不够。

## Consequences

- Positive: 具体收益。
- Negative: 具体代价、上限,以及什么情况下应该重新评估。
```

头部字段:

- `Status`:必填,取值 `proposed` / `accepted` / `rejected` / `superseded`。
- `Applies-To`:除 `superseded` 外必填。逗号分隔的路径或 glob(相对仓库根),全局约束写 `project-wide`。它是别的 Agent 按路径找到这篇笔记的主要入口,写宽了没用,写错了会失效,所以改文件名或移目录时要一并更新。`rejected` 也要写:填「该方案若被重新提出,会落在哪些路径」,通常是它当时瞄准的模块;仓库级选型写 `project-wide`,不要为了凑字段编一个不存在的路径。
- `Superseded-By`:只在 `superseded` 时出现,值是同目录下的文件名。

四个二级标题 `Context`、`Decision`、`Alternatives`、`Consequences` 固定,顺序固定,不加别的二级标题。

### 各状态的含义

- **proposed**:方案已形成,但尚未定案或尚未落地。可以先记录 proposed;只有所需取舍未获授权、存在未解决的需求分歧或必须由用户决定时,才需要询问。
- **accepted**:当前项目实际遵循的决策。用户已经明确拍板、授权相关技术选择或迁移,或把选型委托给你时,可以继续实施并直接写 accepted,不必重复确认或先走 proposed。
- **rejected**:明确讨论过并否决,且未来仍有参考价值。`Decision` 一节写被否决的方案是什么,`Alternatives` 写最后采用了什么(通常是维持现状),`Consequences` 写不做的代价。
- **superseded**:曾经有效,已被新决策完全取代。

## 5. 写作规则

**accepted 用现在时陈述事实**,不写提案口吻。写「Worker 通过 Message Bus 通信」,不写「将会」「计划」「应该」。笔记跟着代码走,读者是半年后只看当前代码的人,这样才能直接拿它对照现状。

**不写过程叙事**:「经讨论」「本次修改了」「后续 PR 将」「用户要求」都不要出现。这些是会话残留,过一周就失去意义。

**Alternatives 只写真正考虑过的方案**,不要为凑模板编造。每一项写清它为什么在当前约束下合理,以及为什么没有采用。「不做 / 复用现有方案」只有在确实评估过时才写。

只有确实没有任何备选时才可以写:

```markdown
## Alternatives

None — 遵循 [某篇已有约束笔记](./2026-08-01-example.md)。
```

`None` 必须链接到一篇已有笔记,这是为了防止它成为偷懒的默认选项。

**Consequences 必须同时有 Positive 和 Negative**,写成 `- Positive: ...` 和 `- Negative: ...` 的形式。只记录真实、具体的收益与代价;Negative 尽量具体到成本、上限或重新评估的条件。若暂时无法识别具体代价,重新检查约束和备选,不要编造一个来填模板。

篇幅通常 20–60 行。超过 100 行,多半是把过程写进去了。

## 6. 代码里的反向指针

只在「读代码的人会觉得别扭、想简化,但其实是有意为之」的入口处,用项目语言的注释语法加一行:

```ts
// Decision: 2026-09-21-worker-runtime-boundary.md — Worker 不直接依赖 Main Process
```

一处入口一行就够,不要到处撒。已接入的校验脚本可检查它指向的笔记是否存在。笔记被取代后,回来把注释改指向现行笔记。

## 7. 收尾清单

改完代码、准备结束之前逐项过一遍:

1. 这次改动有没有改变某篇 accepted 笔记里的事实(名称、路径、行为)?按第 3 节判断:非核心事实变化就更新原笔记,核心结论变化就新建并取代。
2. 新笔记的 `Status`、`Applies-To`、链接是否正确,`Applies-To` 是否覆盖了实际改动的路径?
3. 本次任务里创建的 `proposed` 是否已经定案?按结果处理,不要留下含义不明的 `proposed`:
   - 已经落地生效 → 改为 `accepted`。
   - 方案被否决 → 改为 `rejected`。
   - 决定暂缓(用户明确暂缓,或已授权但尚未实施) → 保持 `proposed`,并在最终回复里说明暂缓原因。
   - 未获授权、或仍有必须由用户决定的取舍 → 询问。
4. 笔记和代码放在**同一次提交**里。只改代码不改笔记,是笔记腐烂最常见的方式。
5. 本次新增或修改了笔记、修改了 `Decision:` 指针,或移动/删除了笔记关联的文件时,运行项目已接入的结构校验命令。先查项目协作说明与工具配置;若采用 `npm run verify-decisions`,在项目根目录运行并读取输出。检查文件命名、字段、章节、链接及取代关系,但校验通过不代表设计理由正确,也不能替代第 1 节的约束检索。校验失败时修正实际问题,不要为通过校验填充内容。未接入校验器时,人工检查本次变更的结构和引用,并如实说明未运行自动校验;除非任务包含接入工具,不要擅自新增 npm 脚本、依赖或构建步骤。
6. 在最终回复里用一句话说明新建或更新了哪些笔记。没有涉及笔记就不用提。
